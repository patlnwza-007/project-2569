# YuemDee · ระบบยืม-คืนพัสดุออนไลน์ มหาวิทยาลัยอุบลราชธานี — Use Case Description

> อ้างอิงจาก `yuemdee_functional_requirements.md` (v1.3) — 1 use case ในเอกสารนี้ต้องตรงกับ 1 use case ใน `usecase_overview.puml` + `usecase_module1-10.puml` (UC-01 ถึง UC-38)
> ผู้ใช้งาน 3 บทบาท: 🎓 นักศึกษา (Student), 👷 เจ้าหน้าที่ (Staff), 👑 ผู้ดูแลระบบ (Admin)
> จัดกลุ่มเป็น 10 Module (M1–M10) ตาม Django app หลังยุบรวม (ดูตารางสรุปท้ายเอกสาร) แต่ละ module แบ่งเป็น Epic (E1, E2...) ภายใน
>
> **อัปเดตตาม mockup ปัจจุบัน (เวอร์ชันข้อมูลจำลอง `2026-09-16-durable-material-v6`) — เทียบทุกบรรทัดกับโค้ดจริงใน `docs/mockup/yuemdee/` ไม่ใช่แค่ `mockup_changes_log.md`** เพราะพบว่า log เขียนคลาดเคลื่อนจากโค้ดจริงบางจุด (เช่น อัตราค่าปรับ) รายละเอียดการเปลี่ยนแปลงหลักดูที่ท้ายเอกสารหัวข้อ "บันทึกการอัปเดตรอบนี้"

**หมวดสิ่งของ 3 ประเภท (เปลี่ยนจากเดิม 2 ประเภท — กระทบเกือบทุก use case ในเอกสารนี้):**

| ประเภท (`type`) | นิยาม | ทะเบียนรายชิ้น (Asset Tag) | กำหนดคืน/ค่าปรับ |
|---|---|---|---|
| `material` (วัสดุสิ้นเปลือง) | เบิกใช้แล้วหมดไป ไม่ต้องคืน | ไม่มี | ไม่มี |
| `durable_material` (วัสดุคงทน) | ต้องยืม-คืน แต่นับจำนวนรวม (bulk) | ไม่มี | มี (`max_borrow_days`, ค่าปรับ) |
| `equipment` (ครุภัณฑ์) | ต้องยืม-คืน มีทะเบียนรายชิ้น | มี (`asset_tag` เช่น `UBU-EQ-001-01`) | มี (`max_borrow_days`, ค่าปรับ) |

**หมายเหตุทั่วไป (Cross-cutting concern):** ทุก use case ในเอกสารนี้ (ยกเว้น UC-15 การเข้าสู่ระบบเอง) มีเงื่อนไขก่อนเริ่มทำงานร่วมกันคือ **ผู้ใช้ต้องเข้าสู่ระบบด้วยบริการ UBU Single Sign-On (@ubu.ac.th) และผ่านการตรวจสอบสิทธิ์และบทบาทเรียบร้อยแล้ว (`login_required` + ตรวจสอบ role/permission)** จึงไม่ระบุซ้ำในทุกแถว "เกี่ยวข้องกับ Service/Endpoint อื่น" ของแต่ละ use case ด้านล่าง

**หมายเหตุทั่วไป (การแจ้งเตือน):** เหตุการณ์ต่อไปนี้ ระบบจะแจ้งเตือนนักศึกษาโดยอัตโนมัติเสมอทั้ง 2 ช่องทาง คือ (1) การแจ้งเตือนในหน้าเว็บ (in-app) และ (2) อีเมล — ผลการอนุมัติ/ปฏิเสธคำขอยืม (UC-17), ถึงคิวที่จองไว้ (UC-10), ใกล้ครบกำหนดคืน/เกินกำหนดคืน (ต่อเนื่องจนกว่าจะแจ้งคืนสำเร็จที่ UC-08), ผลการพิจารณาคำเสนอแนะสิ่งของ (UC-28), และผลการตรวจรับเรื่องแจ้งซ่อม (UC-38) — เป็นพฤติกรรมอัตโนมัติของระบบที่ผูกกับ use case ของ actor แต่ละอันตามที่ระบุ ไม่แยกเป็น use case ใหม่ เพราะไม่มี actor ที่ริเริ่มการแจ้งเตือนเองโดยตรง จึงระบุไว้ที่นี่ครั้งเดียวแทนการเขียนซ้ำในทุก use case ที่เกี่ยวข้อง

> **ไม่มีอีกต่อไป (ตัดออกตาม mockup ปัจจุบัน):** สถานะ "อนุมัติแล้ว/รอรับของ" และกติกา auto-expire ถ้าไม่มารับของภายใน 2 วัน — เพราะ flow ปัจจุบันเป็น **On-the-Spot Counter Inspection**: นักศึกษาหยิบของมาวางหน้าเคาน์เตอร์ก่อนแล้วค่อยกดยืนยันคำขอ (`PENDING`) เจ้าหน้าที่ตรวจของจริงแล้วปล่อยทันทีในคลิกเดียว (`BORROWING`/`ISSUED`) ไม่มีช่วงเวลารอระหว่างอนุมัติกับรับของอีกต่อไป (ดู UC-06, UC-17 ที่แก้ไขใหม่)

## M1 · account (บัญชีและการเข้าสู่ระบบ)

> **แก้ไขรอบนี้:** (1) ตัดทุกการอ้างอิง "Whitelist" ออก — รายชื่อบัญชีที่แอดมินเห็น (UC-32) มาจากบันทึกการเข้าสู่ระบบจริงผ่านบัญชี @ubu.ac.th เท่านั้น (2) **กำหนด Flow เข้าสู่ระบบครั้งแรก (First-time Onboarding):** บังคับกรอกรหัสนักศึกษา (11 หลัก), เบอร์โทรศัพท์ (10 หลัก), และชื่อ-นามสกุล ในการล็อกอินครั้งแรก หากเคยเข้าสู่ระบบแล้วจะข้ามขั้นตอนนี้ทันที

### E1 · การเข้าสู่ระบบ (นักศึกษา และ เจ้าหน้าที่)

#### UC-15 · เข้าสู่ระบบ (Dual Authentication: UBU SSO และ Django Admin)

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-17, FR-14, FR-15 |
| **Actor หลัก** | นักศึกษา (Student), เจ้าหน้าที่ (Staff), ผู้ดูแลระบบ (Admin) |
| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | ระบบรองรับการเข้าสู่ระบบแบบ 2 ช่องทาง (Dual Authentication):<br>1. **นักศึกษาและเจ้าหน้าที่ (UBU SSO):** เข้าสู่ระบบด้วยบัญชีอีเมลมหาวิทยาลัย (@ubu.ac.th) ผ่าน UBU Single Sign-On (Google OAuth 2.0) โดยหากเป็นการเข้าสู่ระบบครั้งแรก (First-time Login) นักศึกษาจะถูกนำทางให้บันทึกรหัสนักศึกษา (11 หลัก) และเบอร์โทรศัพท์ (10 หลัก) ก่อนเข้าใช้งาน<br>2. **ผู้ดูแลระบบ (Admin / Superuser):** เข้าสู่ระบบด้วยบัญชี Local Database (Username / Password) บัญชีเดียวกับ Django Admin Backend (`/admin/`) โดยตรง ไม่ต้องใช้อีเมล UBU SSO เพื่อความปลอดภัยและการบริหารจัดการเซิร์ฟเวอร์ |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | **กรณี นศ./เจ้าหน้าที่:** มีบัญชีอีเมลมหาวิทยาลัย (@ubu.ac.th) ที่ถูกต้อง<br>**กรณี Admin:** มีบัญชี Superuser ในฐานข้อมูล Django (สร้างผ่าน `python manage.py createsuperuser`) |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | **ช่องทางที่ 1: นักศึกษาและเจ้าหน้าที่ (UBU SSO Flow):**<br>1. ผู้ใช้เลือก "เข้าสู่ระบบด้วย UBU SSO"<br>2. ระบบส่งผู้ใช้ไปยืนยันตัวตนผ่านบริการ UBU Single Sign-On (Google OAuth @ubu.ac.th)<br>3. เมื่อยืนยันตัวตนสำเร็จ ระบบตรวจสอบประวัติบัญชีผู้ใช้ในระบบ:<br>&nbsp;&nbsp;&nbsp;&nbsp;**ก. เข้าสู่ระบบครั้งแรก (นศ.):** บันทึกข้อมูลส่วนตัว (รหัสนักศึกษา 11 หลัก, เบอร์โทร 10 หลัก)<br>&nbsp;&nbsp;&nbsp;&nbsp;**ข. เคยเข้าสู่ระบบแล้ว:** ข้ามขั้นตอนกรอกข้อมูลทันที<br>4. ตรวจสอบ Role Override (UC-33) หากมีให้ปรับใช้บทบาทพิเศษ<br>5. สร้างเซสชันและนำเข้าสู่หน้าหลักตามบทบาท (นศ. เข้าหน้าคำขอ, เจ้าหน้าที่เข้าหน้าแดชบอร์ด)<br><br>**ช่องทางที่ 2: ผู้ดูแลระบบ (Django Admin Local Flow):**<br>1. ผู้ดูแลระบบเลือกแท็บ "เข้าสู่ระบบผู้ดูแลระบบ (Django Admin)"<br>2. กรอก Username และ Password ของ Django Superuser แล้วกดยืนยัน<br>3. ระบบตรวจสอบข้อมูลกับฐานข้อมูลบัญชีผู้ใช้ของ Django (`django.contrib.auth.authenticate`)<br>4. เมื่อยืนยันตัวตนถูกต้อง ระบบสร้างเซสชันระดับ Superuser และนำเข้าสู่หน้าแดชบอร์ดจัดการผู้ใช้ (Admin Panel) ทันที โดยเซสชันนี้สามารถใช้เปิดเข้าหน้า Django Admin Backend (`/admin/`) ควบคู่ได้โดยไม่ต้องล็อกอินซ้ำ |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | - หากการยืนยันตัวตนกับ Google OAuth ไม่สำเร็จ หรืออีเมลไม่ลงท้ายด้วย `@ubu.ac.th` ระบบปฏิเสธการเข้าสู่ระบบ<br>- หากกรอก Username หรือ Password ของ Admin ไม่ถูกต้อง ระบบแสดงข้อความแจ้งเตือน "ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง"<br>- หากบัญชีถูกระงับสิทธิ์ (Block) โดยแอดมิน ระบบปฏิเสธการเข้าสู่ระบบ<br>- หากรหัสนักศึกษาหรือเบอร์โทรศัพท์ในขั้นตอน First-time Login ไม่ถูกต้องตามรูปแบบ ระบบแจ้งเตือนให้แก้ไขก่อนเข้าสู่ระบบ |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | ผู้ใช้มีเซสชันที่ยืนยันตัวตนแล้ว และเข้าใช้งานฟังก์ชันตามบทบาทจริงของตนได้สมบูรณ์ |
| **ความสัมพันธ์กับ Use Case อื่น** | เป็นเงื่อนไขก่อนเริ่มงาน (pre-condition) ร่วมของทุก use case อื่นในเอกสารนี้ |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **สถาปัตยกรรม Dual Authentication:**<br>1. **ผู้ใช้ทั่วไป (Student/Staff):** ผูกกับการยืนยันตัวตนผ่าน UBU SSO เท่านั้น ไม่มีการเก็บรหัสผ่านไว้ในระบบ YuemDee<br>2. **ผู้ดูแลระบบ (Admin):** ใช้ระบบยืนยันตัวตนเฉพาะของ Django (`auth_user`) สามารถเข้าถึงระบบได้แม้บริการภายนอกหรือเครือข่าย SSO ขัดข้อง (Break-glass access)<br>3. **กฎการตรวจสอบความถูกต้องของข้อมูล (Validation Rules):** รหัสนักศึกษา 11 หลัก (`^\d{11}$`) ไม่ซ้ำกัน, เบอร์โทรศัพท์ 10 หลัก (`^0[689]\d{8}$`) |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `account:sso_login`, `account:admin_login`, `account:onboarding_setup` → `SSOLoginView`, `AdminLoginView`, `FirstTimeSetupView` |

### E2 · ข้อมูลส่วนตัว (Student)

#### UC-13 · จัดการข้อมูลส่วนตัว

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-14, FR-15 |
| **Actor หลัก** | นักศึกษา (Student) |
| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | นักศึกษาต้องการดูข้อมูลส่วนตัวของตนเองในโหมดดูข้อมูล และกดปุ่มแก้ไขเพื่อปรับปรุงข้อมูลติดต่อ (เบอร์โทรศัพท์ 10 หลัก) ให้เป็นปัจจุบันและครบถ้วนสำหรับการยืมสิ่งของ พร้อมทั้งดูวันที่เข้าสู่ระบบครั้งแรก (First Login) และวันเวลาเข้าสู่ระบบครั้งล่าสุด (Last Login) ของตนเอง |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | นักศึกษาเข้าสู่ระบบแล้ว |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. นักศึกษาเปิดหน้าโปรไฟล์ส่วนตัว<br>2. ระบบแสดงข้อมูลส่วนตัวใน**โหมดดูข้อมูล (View Mode)** ได้แก่ รหัสนักศึกษา (11 หลัก), ชื่อ-นามสกุล, อีเมล, เบอร์โทรศัพท์ (10 หลัก), วันที่เข้าสู่ระบบครั้งแรก และวันเวลาเข้าสู่ระบบครั้งล่าสุด พร้อมปุ่ม `[ ✏️ แก้ไขข้อมูลส่วนตัว ]`<br>3. นักศึกษากดปุ่ม `[ ✏️ แก้ไขข้อมูลส่วนตัว ]` เพื่อขอแก้ไขข้อมูล<br>4. ระบบสลับเข้าสู่**โหมดแก้ไข (Edit Mode)** โดยเปิดช่องให้แก้ไขเบอร์โทรศัพท์ พร้อมแสดงปุ่ม `[ ✓ บันทึกข้อมูล ]` และปุ่ม `[ ยกเลิก ]` (โดยรหัสนักศึกษาและอีเมลจะถูกล็อกไว้ในสถานะอ่านได้อย่างเดียว)<br>5. นักศึกษาแก้ไขเบอร์โทรศัพท์ติดต่อ (10 หลัก) แล้วกดปุ่ม `[ ✓ บันทึกข้อมูล ]`<br>6. ระบบตรวจสอบความถูกต้องของเบอร์โทรศัพท์ (ตัวเลข 10 หลัก)<br>7. ระบบบันทึกข้อมูลลงฐานข้อมูล สลับกลับสู่โหมดดูข้อมูลปกติ และแสดงข้อความแจ้งเตือน "บันทึกข้อมูลส่วนตัวสำเร็จ" |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากนักศึกษากดปุ่ม `[ ยกเลิก ]` ในโหมดแก้ไข ระบบจะยกเลิกการเปลี่ยนแปลง คืนค่าเดิม และสลับกลับสู่โหมดดูข้อมูล<br>หากเบอร์โทรศัพท์ไม่ถูกต้อง (ไม่ใช่ตัวเลข หรือไม่ครบ 10 หลัก) ระบบแสดงข้อความแจ้งเตือน "กรุณากรอกเบอร์โทรศัพท์ให้ถูกต้อง (เป็นตัวเลข 10 หลัก)" และไม่อนุญาตให้บันทึก<br>หากข้อมูลติดต่อยังไม่ครบและนักศึกษาพยายามส่งคำขอยืม (UC-06) ระบบจะบังคับพากลับมาที่หน้านี้พร้อมเปิดโหมดแก้ไขให้อัตโนมัติ (ตาม FR-15) |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | ข้อมูลเบอร์โทรศัพท์ติดต่อของนักศึกษาถูกอัปเดตและเป็นปัจจุบัน และหน้าจอสลับกลับมาอยู่ในโหมดดูข้อมูล |
| **ความสัมพันธ์กับ Use Case อื่น** | รับข้อมูลตั้งต้นจากการลงทะเบียนครั้งแรกใน UC-15; เป็นเงื่อนไขก่อนเริ่มงาน (pre-condition) ของ UC-06 |

| **คำอธิบายโดยย่อ** | นักศึกษาต้องการส่งคำขอยืม/เบิกสิ่งของหลายชิ้นพร้อมกันในคราวเดียว หลังจากไปหยิบสิ่งของจากตู้/ชั้นวางมาวางที่หน้าเคาน์เตอร์แล้ว โดยไม่ต้องกรอกเหตุผลการยืมใดๆ ทั้งสิ้น (ไม่มีฟิลด์เหตุผลในระบบตามโครงสร้างฐานข้อมูลปัจจุบัน) เว้นแต่ต้องการขอยืมระยะยาวเป็นกรณีพิเศษจะระบุเฉพาะวันที่ต้องการคืนเอง |

| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | มีคำขอยืมสถานะ "รอเจ้าหน้าที่ตรวจของ" (`PENDING`) ถูกสร้างขึ้น พร้อมรูปหลักฐานสภาพเดิม (ถ้าแนบ) รอเจ้าหน้าที่ตรวจของจริงหน้าเคาน์เตอร์ (UC-17) |
| **ความสัมพันธ์กับ Use Case อื่น** | `<<include>>` UC-05 (ต้องมีตะกร้าก่อนเสมอ); เป็นฐานของ UC-17 (เจ้าหน้าที่ตรวจของและปล่อยของ) |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **ไม่ต้องกรอกเหตุผล:** การส่งคำขอยืมทั้งกรณีปกติและกรณีขอยืมระยะยาวพิเศษไม่ต้องกรอกเหตุผลใดๆ ทั้งสิ้น (ตัดฟิลด์เหตุผลออกจากระบบและโมเดลฐานข้อมูล `BORROW_REQUEST` แล้ว) · **วันที่เริ่มใช้งาน:** นักศึกษาไม่ต้องกรอกเอง ระบบบันทึก `use_date` ให้อัตโนมัติ · **ขอยืมพิเศษ:** ติ๊กเลือกเฉพาะกรณีต้องการยืมนานกว่าปกติ/ทั้งเทอม/งานวิจัย บังคับระบุเฉพาะวันที่ต้องการคืนเอง (`custom_due_date`) เท่านั้น |

#### UC-08 · แจ้งคืนสิ่งของ (ครุภัณฑ์และวัสดุคงทน)

| หัวข้อ | รายละเอียด |

| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | นักศึกษาต้องการแจ้งคืนสิ่งของประเภทครุภัณฑ์และวัสดุคงทนผ่านระบบ (วัสดุสิ้นเปลืองไม่ต้องคืน) เมื่อต้องการนำของมาคืนที่คลัง โดยเลือกได้ว่าจะทยอยคืนเฉพาะบางชิ้นในคำขอเดียวกันหรือคืนพร้อมกันทั้งหมด พร้อมระบุสภาพและถ่ายรูปหลักฐาน ณ วันคืน |

| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากไม่ได้แนบรูปภาพสภาพ ณ วันคืน ระบบแจ้งเตือนให้ถ่ายรูป/แนบรูปหลักฐานก่อนกดยืนยัน<br>นักศึกษายกเลิกการแจ้งคืนได้หากยังไม่สะดวกนำของมาจริง (กลับไปสถานะ "กำลังยืม" ตามเดิม) |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | คำขอมีสถานะ "รอเจ้าหน้าที่ตรวจรับคืน" พร้อมรูปภาพและสภาพที่แจ้งไว้ต่อชิ้น รอเจ้าหน้าที่ตรวจรับ (UC-18); หน้ารายการคำขอของนักศึกษาแสดงแบนเนอร์เตือนให้นำของมาแสดงที่เคาน์เตอร์ |
| **ความสัมพันธ์กับ Use Case อื่น** | เป็นฐานของ UC-18 (เจ้าหน้าที่ตรวจรับคืน) |

| **คำอธิบายโดยย่อ** | นักศึกษาต้องการจัดการคิวของตนเองแบบครบวงจร โดยจองคิวได้ 2 ระดับ: (ก) ระดับสิ่งของรวม (item-level) เมื่อวัสดุคงทนถูกยืมหมด และ (ข) ระดับรหัสครุภัณฑ์เฉพาะชิ้น (unit-level) เมื่อชิ้นนั้นถูกยืมอยู่ แม้ครุภัณฑ์รุ่นเดียวกันชิ้นอื่นจะยังว่างอยู่ก็ตาม |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | **กรณี item-level (วัสดุคงทน):** สิ่งของนั้นมีจำนวนคงเหลือรวมเป็น 0 · **วัสดุสิ้นเปลืองจองคิวไม่ได้** · **กรณี unit-level (ครุภัณฑ์):** รหัส Asset Tag ชิ้นที่เลือกมีสถานะ "ถูกยืมอยู่" (`BORROWED`) — ไม่เกี่ยวกับว่าครุภัณฑ์รุ่นเดียวกันชิ้นอื่นยังว่างอยู่หรือไม่ |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. นักศึกษากดจองคิวจากหน้ารายการ/รายละเอียดสิ่งของ — เลือกจองคิว item รวม (วัสดุคงทนหมดสต็อก) หรือจองคิวเฉพาะรหัส Asset Tag (ครุภัณฑ์ชิ้นที่ถูกยืมอยู่)<br>2. ระบบเพิ่มนักศึกษาเข้าคิว แจ้งลำดับที่ และ**แสดงประมาณการวันที่คาดว่าจะสามารถยืมของได้คร่าวๆ (Estimated Available Date)** ทันทีผ่านหน้าต่างป๊อปอัปแจ้งเตือน โดยระบบคำนวณจากกำหนดส่งคืนจริงของผู้ยืมคนปัจจุบัน (`due_date`) ซึ่งครอบคลุมกรณีที่ผู้ยืมปัจจุบันได้รับอนุมัติขอยืมนานพิเศษ (Special Extended Borrowing เช่น สำหรับทำโครงงาน/วิจัย) และคำนวณสะสมตามลำดับคิวก่อนหน้า<br>3. นักศึกษาเปิดหน้ารายการคิวที่จองอยู่เพื่อติดตามลำดับ โดยระบบแสดงการ์ดประมาณการวันที่คาดว่าจะได้ยืมอย่างชัดเจน พร้อมข้อความชี้แจง (เช่น ผู้ยืมปัจจุบันมีกำหนดคืนวันที่เท่าใด หรือได้รับอนุมัติยืมนานพิเศษ)<br>4. เมื่อถึงคิวของนักศึกษาคนนั้น ระบบแจ้งเตือนผ่านหน้าเว็บและอีเมลทันที (`notified_at`) และนักศึกษาต้องกดยืนยันรับสิทธิ์คิวภายใน 1 วัน — เมื่อกดยืนยัน ระบบเปลี่ยนสถานะคิวเป็น `CONFIRMED` (`confirmed_at`)<br>5. นักศึกษากดออกจากคิวเมื่อไม่ต้องการยืมแล้ว |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากสิ่งของ/ชิ้นนั้นมีจำนวนคงเหลือ/ว่างอยู่แล้วในขณะนั้น ระบบไม่อนุญาตให้จองคิวและแนะนำให้ยืมได้ทันที<br>หากนักศึกษาอยู่ในคิวเดียวกันอยู่แล้ว ระบบแจ้งเตือน "คุณอยู่ในคิวแล้ว" ไม่ให้จองซ้ำ<br>**หากนักศึกษาไม่กดยืนยันรับสิทธิ์ภายใน 1 วันหลังได้รับแจ้งเตือนว่าถึงคิว** ระบบถือว่าสละสิทธิ์โดยอัตโนมัติ (`expired_at`, สถานะ `EXPIRED`) และแจ้งเตือนคิวถัดไปทันที |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | คิวของนักศึกษาถูกสร้าง/ยกเลิกตามที่ดำเนินการ; นักศึกษาทราบประมาณการวันที่คาดว่าจะได้ยืมสิ่งของ; เมื่อสิ่งของ/ชิ้นนั้นว่างและถึงคิวของนักศึกษาคนนั้น ระบบแจ้งเตือนผ่านหน้าเว็บและอีเมลทันที พร้อมเริ่มนับเวลา 1 วันสำหรับการกดยืนยันรับสิทธิ์ |
| **ความสัมพันธ์กับ Use Case อื่น** | `<<extend>>` จาก UC-05 (จองคิวแทนเมื่อถูกตัดหน้าในตะกร้า) และ UC-03 (จองคิวจากหน้ารายละเอียด) |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **1. แยกระดับคิวให้ชัด:** คิวระดับ item (ไม่มี `asset_tag`) ใช้กับวัสดุคงทน ส่วนคิวระดับ unit (มี `asset_tag`) ใช้กับครุภัณฑ์เท่านั้น เนื่องจากครุภัณฑ์ 1 รายการในระบบคือ 1 ชิ้นตาม `asset_tag` คิวของครุภัณฑ์จึงเป็นคิวของชิ้นนั้นโดยตรง · วัสดุสิ้นเปลืองจองคิวไม่ได้ · **สถานะคิว:** `WAITING` (รอคิว) → `NOTIFIED` (ถึงคิว แจ้งเตือนแล้ว) → `CONFIRMED` (ยืนยันรับสิทธิ์แล้ว) หรือ `EXPIRED` (ไม่ยืนยันภายใน 1 วัน) · `CANCELLED` (ออกจากคิวเอง)<br>**2. การคำนวณและแจ้งประมาณการวันพร้อมยืม (Estimated Available Date):** เมื่อนักศึกษาจองคิว ระบบจะคำนวณและแจ้งวันที่คาดว่าจะพร้อมให้ยืมคร่าวๆ ทันที โดยอิงจากกำหนดส่งคืนจริง (`due_date`) ของผู้ที่กำลังยืมอยู่ปัจจุบัน ซึ่งครอบคลุมกรณีที่ผู้ยืมได้รับอนุมัติขอยืมนานพิเศษ (Special Extended Borrowing เช่น ยืมทำโครงงาน 14-30 วัน) บวกระยะเวลาตรวจรับและรอบเวลายืมของคิวก่อนหน้าตามลำดับ<br>**3. กติกาหมดเวลาคิว (ยืนยันกับผู้ใช้แล้ว 16 ก.ย. 2569):** เมื่อถึงคิวและระบบแจ้งเตือนแล้ว (`notified_at`) นักศึกษามีเวลา **1 วัน** ในการกดยืนยันรับสิทธิ์ หากไม่กดยืนยันภายในเวลาดังกล่าว ระบบถือว่าสละสิทธิ์โดยอัตโนมัติ (`expired_at`, สถานะ `EXPIRED`) และเลื่อนคิวให้นักศึกษาคนถัดไปทันที |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `borrow:queue_join`, `borrow:queue_list`, `borrow:queue_leave` → `QueueJoinView`, `QueueListView`, `QueueLeaveView` |

## M5 · evaluation (การประเมินความพึงพอใจและรีวิว)

> **แก้ไขรอบนี้:** UC-14 เดิมไม่มี flow เขียนรีวิวผูก Asset Tag (conflict ที่ค้างมาจากรอบตรวจก่อนหน้า) — mockup ปัจจุบัน **มีการเขียนรีวิวจริงแล้ว** ที่หน้าประเมิน จึงรวมเข้าเป็น flow เดียวกับ UC-14 (ประเมินทีละชิ้นอิสระ + เขียนรีวิวอัตโนมัติเมื่อชิ้นนั้นเป็นครุภัณฑ์)

### E1 · การประเมินของนักศึกษา

#### UC-14 · ประเมินความพึงพอใจรายชิ้นและเขียนรีวิว

| หัวข้อ | รายละเอียด |

| **รหัสอ้างอิง** | FR-16 |
| **Actor หลัก** | นักศึกษา (Student) |
| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | นักศึกษาต้องการประเมินความพึงพอใจและสภาพการใช้งานของสิ่งของที่คืนแล้ว **แยกเป็นรายชิ้นอย่างอิสระ** (ไม่ถูกบังคับให้ประเมินพร้อมกันทุกชิ้นในคำขอเดียวกัน) โดยสำหรับครุภัณฑ์ คะแนนดาวและข้อความรีวิวจะถูกบันทึกผูกเข้ากับรหัส Asset Tag ของชิ้นนั้นโดยอัตโนมัติ เพื่อให้ผู้ยืมคนถัดไปใช้ประกอบการตัดสินใจ (ดู UC-37) |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | นักศึกษาเข้าสู่ระบบแล้ว และมีสิ่งของที่คืนสำเร็จแล้วอย่างน้อย 1 ชิ้นที่ยังไม่เคยประเมิน |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. นักศึกษาเปิดหน้าประเมิน (จากเมนู หรือกดปุ่ม `⭐ ประเมินชิ้นนี้` จากหน้ารายการคำขอ/ประวัติ UC-09/UC-11)<br>2. ระบบแสดงแถบการ์ดรายชิ้นของสิ่งของที่คืนแล้วทั้งหมด พร้อมสถานะ: `✓ ประเมินแล้ว (คะแนน)` / `⭐ รอประเมิน` / `✍️ กำลังประเมิน`<br>3. นักศึกษาเลือกชิ้นที่ต้องการประเมิน ให้คะแนนดาว 1-5 ดาว และเขียนข้อความรีวิวสภาพสิ่งของ<br>4. กดยืนยันการส่งแบบประเมินของชิ้นนั้น<br>5. ระบบบันทึกผลการประเมินลงตาราง `REVIEW` ผูกกับรายการยืมชิ้นนั้น (`borrow_item_id`)<br>6. **หากชิ้นนั้นเป็นครุภัณฑ์ (มีรหัส Asset Tag)** รีวิวนั้นจะปรากฏในประวัติรีวิวของรหัส Asset Tag ชิ้นนั้นโดยอัตโนมัติ (ผูกกับชิ้นนั้นเท่านั้น ไม่ใช่ผูกรวมทั้งรุ่น) และคำนวณคะแนนดาวเฉลี่ยของชิ้นนั้นใหม่<br>7. ระบบเลื่อนไปยังชิ้นถัดไปที่ยังไม่ได้ประเมินโดยอัตโนมัติ (ถ้ามี) |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากชิ้นนั้นถูกประเมินไปแล้ว ระบบแสดงผลการประเมินเดิมแทนฟอร์มกรอกใหม่ (ไม่ให้ประเมินซ้ำ) |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | ผลการประเมินของชิ้นนั้นถูกบันทึก และหากเป็นครุภัณฑ์ รีวิว/คะแนนดาวของรหัส Asset Tag ชิ้นนั้นถูกอัปเดตให้ผู้ยืมคนถัดไปเห็นทันที (UC-37) |
| **ความสัมพันธ์กับ Use Case อื่น** | ต่อเนื่องจาก UC-08/UC-18 (คืนสำเร็จ); เขียนข้อมูลที่ UC-37 นำไปแสดง |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **ประเมินได้ 1 ครั้งต่อชิ้น** ไม่ใช่ 1 ครั้งต่อแบบฟอร์มทั้งชุดเหมือนเดิม — นักศึกษาประเมินแต่ละชิ้นในคำขอเดียวกันแยกอิสระได้ **ผูกรีวิวกับ Asset Tag รายชิ้น:** เฉพาะชิ้นที่เป็นครุภัณฑ์เท่านั้นที่มีการเขียนรีวิวเก็บสะสมต่อรหัสชิ้น วัสดุ/วัสดุคงทนบันทึกผลประเมินไว้ที่ `REVIEW` เช่นกัน แต่ไม่ผูกกับ asset tag ใด |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `evaluation:submit` → `EvaluationSubmitView` (บันทึกลงตาราง `REVIEW`) |

| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | หากคำขอมีครุภัณฑ์หรือวัสดุคงทนแม้แต่ชิ้นเดียว → คำขอเปลี่ยนเป็น "กำลังยืม" (`BORROWING`) ทันที พร้อมกำหนดวันคืนรายชิ้น (`BORROW_ITEM.due_date` = วันปล่อยของ + `max_borrow_days` ของสิ่งของชิ้นนั้น · คำขอพิเศษใช้ `custom_due_date` ที่อนุมัติกับทุกรายการ · วัสดุสิ้นเปลืองไม่มีกำหนดคืน); หากมีเฉพาะวัสดุสิ้นเปลืองล้วน → คำขอเปลี่ยนเป็น "เบิกสำเร็จ" (`ISSUED`) ทันที; หรือคำขอเปลี่ยนเป็น "ปฏิเสธแล้ว" (`REJECTED`) พร้อมเหตุผล — ทุกกรณีส่งแจ้งเตือนให้นักศึกษา |
| **ความสัมพันธ์กับ Use Case อื่น** | ต่อยอดจาก UC-06 (นักศึกษาส่งคำขอ); ยุบรวมขั้นตอน "ยืนยันรับสิ่งของ" (อดีต FR-08) เข้ามาในขั้นตอนที่ 6 |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **ตัดจ่ายอัตโนมัติตามรหัสที่เลือก:** เจ้าหน้าที่ไม่ต้องกดเลือก Dropdown สลับรหัสชิ้น ระบบตัดจ่ายตามรหัส Asset Tag ที่นักศึกษาเลือกไว้ตอนลงตะกร้า/ส่งคำขอ · **ไม่มีสถานะ "อนุมัติแล้ว/รอรับของ" อีกต่อไป** และไม่มี auto-expire 2 วัน เพราะอนุมัติกับรับของเกิดขึ้นพร้อมกันเสมอ · **อนุญาตให้ตรวจปล่อยของคำขอตนเองได้:** สำหรับเจ้าหน้าที่ที่มีบทบาทควบคู่ (นักศึกษาที่ได้รับสิทธิ์เจ้าหน้าที่ผ่าน Role Override) ระบบอนุญาตให้เจ้าหน้าที่สามารถตรวจนับสิ่งของและกดปล่อยของให้กับคำขอยืมที่ตนเองเป็นผู้ยืมได้โดยตรง เพื่อความคล่องตัวในการใช้งานและการปฏิบัติงานจริง |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `staff:request_list`, `staff:request_approve`, `staff:request_reject` → `RequestApproveRejectView` |

#### UC-18 · ตรวจรับคืนสิ่งของหน้าเคาน์เตอร์ (Counter Return Terminal)

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-20 |
| **Actor หลัก** | เจ้าหน้าที่ (Staff) |
| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | เจ้าหน้าที่ต้องการตรวจรับคืนสิ่งของที่นักศึกษานำมาคืนที่เคาน์เตอร์ โดยตรวจสภาพจริงเทียบกับที่นักศึกษาแจ้งไว้ (UC-08) รองรับการคืนบางส่วน จัดการยอดชดใช้กรณีสูญหาย และคำนวณ/แก้ไขค่าปรับเกินกำหนด |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | คำขอมีสถานะ "รอเจ้าหน้าที่ตรวจรับคืน" (`RETURN_PENDING`) หรือมีบางชิ้นแจ้งคืนมาแล้ว (ที่นักศึกษาแจ้งคืนมาจาก UC-08) |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. เจ้าหน้าที่เปิดหน้ารับคืนพัสดุ — กรองแท็บได้: ทั้งหมด / รอตรวจรับคืน / เกินกำหนด / คืนบางส่วน<br>2. ชิ้นที่นักศึกษาแจ้งคืนมาแล้วถูกติ๊กนำร่องให้อัตโนมัติ (Smart Pre-check) เจ้าหน้าที่ตรวจของจริงบนโต๊ะเทียบกับที่ติ๊กไว้ (ใช้ปุ่ม `✓ เลือกทั้งหมด` ได้)<br>3. ต่อแต่ละชิ้นที่ตรวจ เลือกผลตรวจสภาพจริง: **ปกติ** (คืนสต็อกเข้าคลัง, ครุภัณฑ์กลับเป็น `AVAILABLE`) / **ชำรุด** (ครุภัณฑ์เปลี่ยนเป็น `DAMAGED` ไม่คืนสต็อก และสร้างรายการแจ้งซ่อมอัตโนมัติ — เชื่อม UC-35) / **สูญหาย** (ครุภัณฑ์รายชิ้นเปลี่ยนเป็น `LOST` และไม่นับรวมในจำนวนทั้งหมดอีก ส่วนวัสดุคงทนตัดสต็อกรวมถาวร `qty_total -= จำนวนที่หาย`, ระบบตั้งยอดชดใช้เริ่มต้นจากราคาจัดซื้อเดิม ปรับแก้ได้ พร้อมปุ่มบันทึกรับชำระเงิน)<br>4. ระบบคำนวณค่าปรับเกินกำหนดอัตโนมัติเป็นรายชิ้นจากจำนวนวันที่เกิน `due_date` ของแต่ละชิ้น (ดู UC-36) เจ้าหน้าที่กด `✏️ แก้ไขยอดเงิน` เพื่อปรับยอด (`custom_fine`) และกดสลับสถานะ `fine_paid` เมื่อนักศึกษาชำระแล้วได้<br>5. กดยืนยันรับคืน |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | **คืนครบทุกชิ้นที่ต้องคืน** → คำขอเปลี่ยนเป็น "คืนสำเร็จ" (`RETURNED`) สมบูรณ์<br>**คืนบางชิ้น** (ของขาด/ยังใช้ต่อ) → รับคืนเฉพาะชิ้นที่นำมา ชิ้นที่ขาดคงสถานะ "กำลังยืม" (`BORROWING`) ต่อไป และแสดงข้อความสรุป เช่น "คืนแล้ว 1 ชิ้น (ยังค้างส่งอีก 1 ชิ้น)" (คำนวณจากจำนวนที่คืนเทียบกับจำนวนที่ยืม ไม่ได้เก็บเป็นฟิลด์แยก) |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | คำขอเปลี่ยนสถานะตามผลตรวจ (คืนสำเร็จ/คืนบางส่วน) พัสดุที่สภาพปกติถูกคืนเข้าคลังพร้อมให้ยืมต่อ ครุภัณฑ์ชำรุดเข้าสู่ระบบแจ้งซ่อม (UC-35) ครุภัณฑ์สูญหายถูกตัดออกจากคลังถาวรพร้อมบันทึกยอดชดใช้ และบันทึกค่าปรับ/สถานะการชำระเงินเรียบร้อย |
| **ความสัมพันธ์กับ Use Case อื่น** | รับช่วงต่อจาก UC-08 (นักศึกษาแจ้งคืน); ทำงานร่วมกับ UC-36 (จัดการค่าปรับ); ส่งต่อไปยัง UC-35 (ครุภัณฑ์เสียหาย) กรณีชำรุด |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **คืนสต็อกอัตโนมัติเฉพาะกรณีปกติ:** เพิ่มจำนวนพร้อมใช้งานกลับเข้าคลังเฉพาะชิ้นที่ตรวจสภาพปกติเท่านั้น · **ชำรุด→เปลี่ยนสถานะทันที ไม่ต้องรอ UC-23:** ครุภัณฑ์ที่ตรวจพบว่าเสียหายเปลี่ยนเป็น "ครุภัณฑ์เสียหาย" อัตโนมัติทันทีที่ตรวจรับคืน · **สูญหาย→ตัดสต็อกถาวร:** ต่างจากชำรุดตรงที่ตัด `qty_total` ถาวรทันที ไม่ใช่แค่เปลี่ยนสถานะรอซ่อม |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `staff:return_list`, `staff:return_confirm`, `staff:edit_fine` → `ReturnConfirmView` |

### E3 · การจัดการค่าปรับเกินกำหนดและประวัติรีวิว (Fine & Review Management)

#### UC-36 · กำหนดอัตราค่าปรับและจัดการการชำระค่าปรับเกินกำหนด

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-26, FR-37 |
| **Actor หลัก** | เจ้าหน้าที่ (Staff), ผู้ดูแลระบบ (Admin) |
| **Actor รอง** | นักศึกษา (Student) |
| **คำอธิบายโดยย่อ** | เจ้าหน้าที่และแอดมินต้องการคำนวณยอดเงินค่าปรับเกินกำหนดอัตโนมัติเป็นรายชิ้น โดยคิดจาก `จำนวนวันที่เกิน due_date ของชิ้นนั้น × fine_rate_per_day ของสิ่งของ × จำนวนที่คืน` (อัตราค่าปรับกรอกไว้กับสิ่งของแต่ละรายการใน UC-20) ปรับลด/ยกเว้นยอดเงินรายรอบคืน (`custom_fine`) และกดบันทึกสลับสถานะการชำระค่าปรับ (`fine_paid`) เมื่อนักศึกษานำเงินมาชำระ ณ คลัง |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | เจ้าหน้าที่หรือแอดมินเข้าสู่ระบบแล้ว และมีรายการคำขอยืมที่ส่งคืนเกินกำหนด |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. เมื่อตรวจรับคืน (UC-18) ระบบคำนวณค่าปรับของแต่ละรายการที่คืน (`RETURN_ITEM.fine`) = `max(0, วันที่คืน − BORROW_ITEM.due_date) × fine_rate_per_day × qty_returned` และรวมเป็นยอดของรอบคืนนั้น<br>2. ในหน้ารายการรับคืน (UC-18) เจ้าหน้าที่สามารถกดปุ่ม `✏️ แก้ไขยอดเงิน` กรอกยอดเงินค่าปรับใหม่ (`custom_fine`) เพื่อปรับลดหรือยกเว้นค่าปรับเป็น 0 บาทได้<br>3. เมื่อนักศึกษานำเงินมาชำระแล้ว เจ้าหน้าที่กดปุ่มสลับสถานะชำระค่าปรับเป็น "ชำระแล้ว (`fine_paid = true`)" |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากเจ้าหน้าที่ไม่ได้ระบุ `custom_fine` ระบบจะใช้ผลรวม `RETURN_ITEM.fine` ของรอบคืนนั้น<br>หากนักศึกษายังไม่ชำระค่าปรับ สถานะจะแสดงเป็น "ค้างชำระ" และแสดงเตือนในหน้าประวัติยืมของนักศึกษา |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | ยอดค่าปรับรายรอบคืนถูกบันทึก (ยอดรวมของคำขอ = ผลรวมของทุกรอบคืน) และสถานะการชำระเงินถูกบันทึกในระบบ |
| **ความสัมพันธ์กับ Use Case อื่น** | ทำงานร่วมกับ UC-18 (ตรวจรับคืน) |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **คิดค่าปรับรายชิ้น:** ระบบคำนวณค่าปรับเฉพาะสิ่งของประเภทครุภัณฑ์และวัสดุคงทน โดยแต่ละชิ้นนับวันเกินจาก `due_date` ของตัวเอง (ชิ้นในคำขอเดียวกันกำหนดคืนต่างกันได้ตาม `max_borrow_days`) และคิด ณ วันที่คืนชิ้นนั้นจริง ชิ้นที่คืนแล้วใน Partial Return จะไม่ถูกคิดค่าปรับอีก · **อัตราค่าปรับ:** ใช้ `fine_rate_per_day` ที่กรอกไว้กับสิ่งของแต่ละรายการ (UC-20) ไม่มีอัตราเริ่มต้นกลางของระบบ · **สิทธิ์ปรับลดค่าปรับ:** เจ้าหน้าที่และแอดมินมีสิทธิ์กดแก้ไขยอดค่าปรับ (`custom_fine`) หรือยกเว้นค่าปรับ (ตั้งเป็น 0) ได้ตามดุลยพินิจ |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `staff:update_custom_fine`, `staff:toggle_fine_paid` → `FineManagementView` |

| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. เจ้าหน้าที่เปิดหน้าประวัติการยืม-คืนทั้งระบบ<br>2. ระบบรองรับการสลับมุมมอง 2 แท็บ:<br>&nbsp;&nbsp;&nbsp;&nbsp;**ก. แท็บตามใบคำขอยืม (Request Orders):** แสดงรายการ 1 แถว = 1 ใบคำขอ แสดงชื่อนักศึกษา รายการสิ่งของพร้อมรหัส Asset Tag วันที่ยืม/กำหนดคืน และสถานะคำขอ<br>&nbsp;&nbsp;&nbsp;&nbsp;**ข. แท็บติดตามสิ่งของรายชิ้น (Item & Unit Tracking):** คลี่แสดง 1 แถว = 1 ชิ้น/Asset Tag ระบุชัดเจนว่าสิ่งของและรหัส Asset Tag ใด กำลังถูกนักศึกษาคนไหนยืมอยู่ สถานะของชิ้นนั้น และสถานที่ใช้งานปัจจุบัน<br>3. เจ้าหน้าที่สามารถค้นหาตามชื่อ/รหัสนักศึกษา, ชื่อสิ่งของ, รหัส Asset Tag, เลขที่คำขอ และกรองตามสถานะหรือช่วงวันที่ได้<br>4. เจ้าหน้าที่สามารถกดปุ่ม "ดูรายละเอียด" เพื่อเปิดหน้าต่าง Modal แสดงรายละเอียดคำขอยืมแบบเจาะลึก: รายการสิ่งของทุกชิ้น, รหัสประจำชิ้น, สถานะรายชิ้น, ที่ตั้งปัจจุบัน, และรูปถ่ายหลักฐาน |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากไม่พบข้อมูลตามเงื่อนไขค้นหา ระบบแสดงข้อความ "ไม่พบข้อมูล" |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | เจ้าหน้าที่เห็นประวัติการยืม-คืนทั้งในระดับใบคำขอและระดับการติดตามสิ่งของรายชิ้น |
| **ความสัมพันธ์กับ Use Case อื่น** | - |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **การติดตามสถานะรายชิ้น (Unit-level Tracking):** ในแท็บติดตามสิ่งของรายชิ้น สิ่งของประเภทครุภัณฑ์จะผูกกับรหัส Asset Tag รายชิ้นเสมอ ทำให้ตรวจสอบได้ว่าชิ้นใดกำลังถูกยืมหรือส่งคืนแล้ว แม้จะอยู่ในคำขอเดียวกันที่มีการทยอยคืนบางชิ้น (Partial Return) |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `staff:history_all`, `staff:history_detail` → `StaffHistoryAllView`, `StaffHistoryDetailModalView` |

| **ความสัมพันธ์กับ Use Case อื่น** | รับรายการเข้ามาโดยอัตโนมัติจาก UC-18 (แท็บ 1) และจาก UC-38 (แท็บ 2) — คนละรอบเวลา (asynchronous) |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | เมื่อเจ้าหน้าที่ตรวจรับคืนครุภัณฑ์ (UC-18) แล้วพบว่าเสียหาย ระบบต้องเปลี่ยนสถานะรหัสครุภัณฑ์ชิ้นนั้นจาก "พร้อมให้ยืม" เป็น "ครุภัณฑ์เสียหาย" โดยอัตโนมัติทันที ไม่ต้องรอเจ้าหน้าที่ไปตั้งค่าเอง · รายการแจ้งซ่อมจาก UC-38 ไม่ผูกกับประวัติการยืมใดๆ (นักศึกษาแจ้งได้แม้ไม่เคยยืมของชิ้นนั้น) · รองรับการเลือกติ๊กและอัปเดตสถานะพร้อมกันหลายชิ้น (Batch Update) รวมถึงการสั่งปลดระวางแบบกลุ่ม (`RETIRED`) โดยไม่ต้องระบุเหตุผล |

| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | - |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | เจ้าหน้าที่เห็นสถานะคลังสิ่งของและทะเบียนครุภัณฑ์ทุกชิ้นในระบบ |

#### UC-23 · เปลี่ยนสถานะครุภัณฑ์/วัสดุคงทน

| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | รายการที่ถูกเลือกมีสถานะใหม่ และหากไม่พร้อมใช้งานหรือถูกปลดระวางจะถูกตัดออกจากรายการที่พร้อมให้ยืม แต่วิลัยและประวัติยืมเดิมยังคงอยู่ครบถ้วนใน Audit Trail |

| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **1. การแยกการแก้ไขรายชิ้น:** การคลิกปุ่มเปลี่ยนสถานะจากแถวครุภัณฑ์เป็นการแก้ไขเฉพาะรหัสทะเบียน (Asset Tag) นั้น ๆ เพียงชิ้นเดียวเท่านั้น เพื่อความชัดเจนและป้องกันความสับสน<br>**2. การเปลี่ยนสถานะแบบกลุ่ม (Bulk Update):** อนุญาตให้เลือกติ๊กหลายรายการจากหน้าภาพรวมคลังและเปลี่ยนสถานะพร้อมกันผ่าน Modal ได้<br>**3. สถานะปลดระวาง (RETIRED) เฉพาะครุภัณฑ์:** สงวนไว้สำหรับพัสดุประเภทครุภัณฑ์ที่มีรหัส Asset Tag รายชิ้นเท่านั้น และ**ไม่ต้องระบุเหตุผลในการปลดระวาง** (ระบบไม่บังคับกรอกเหตุผล)<br>**4. ห้ามลบข้อมูลครุภัณฑ์/วัสดุคงทนถาวร:** ให้ใช้การเปลี่ยนสถานะ (รวมถึงการปลดระวาง) เพื่อเก็บรักษาประวัติและสถิติการใช้งานย้อนหลัง |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `staff_inventory:equipment_status_update` → `EquipmentStatusUpdateView` |

## ตารางแมปปิ้งระหว่าง Functional Requirement (FR) กับ Use Case (UC)

> **หมายเหตุความสอดคล้อง:**
> - **FR-14** (ดูและแก้ไขข้อมูลส่วนตัว) และ **FR-15** (บังคับกรอกข้อมูลติดต่อก่อนยืม) ถูกยุบรวมเป็น **UC-13 (จัดการข้อมูลส่วนตัว)** เพียง Use Case เดียว
