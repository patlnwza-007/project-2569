# YuemDee · ระบบยืม-คืนพัสดุออนไลน์ มหาวิทยาลัยอุบลราชธานี — Use Case Description

> อ้างอิงจาก `yuemdee_functional_requirements.md` (v1.3) — 1 use case ในเอกสารนี้ต้องตรงกับ 1 use case ใน `usecase_overview.puml` + `usecase_module1-10.puml` (UC-01 ถึง UC-39)
> ผู้ใช้งาน 3 บทบาท: 🎓 นักศึกษา (Student), 👷 เจ้าหน้าที่ (Staff), 👑 ผู้ดูแลระบบ (Admin)
> จัดกลุ่มเป็น 10 Module (M1–M10) ตาม Django app หลังยุบรวม (ดูตารางสรุปท้ายเอกสาร) แต่ละ module แบ่งเป็น Epic (E1, E2...) ภายใน
>
> **อัปเดตตาม mockup ปัจจุบัน (เวอร์ชันข้อมูลจำลอง `2026-09-16-durable-material-v6`) — เทียบทุกบรรทัดกับโค้ดจริงใน `docs/mockup/yuemdee/` ไม่ใช่แค่ `mockup_changes_log.md`** เพราะพบว่า log เขียนคลาดเคลื่อนจากโค้ดจริงบางจุด (เช่น อัตราค่าปรับ) รายละเอียดการเปลี่ยนแปลงหลักดูที่ท้ายเอกสารหัวข้อ "บันทึกการอัปเดตรอบนี้"

**หมวดสิ่งของ 3 ประเภท (เปลี่ยนจากเดิม 2 ประเภท — กระทบเกือบทุก use case ในเอกสารนี้):**

| ประเภท (`type`) | นิยาม | ทะเบียนรายชิ้น (Asset Tag) | กำหนดคืน/ค่าปรับ |
|---|---|---|---|
| `material` (วัสดุสิ้นเปลือง) | เบิกใช้แล้วหมดไป ไม่ต้องคืน | ไม่มี | ไม่มี |
| `durable_material` (วัสดุคงทน) | ต้องยืม-คืน แต่นับจำนวนรวม (bulk) | ไม่มี | มี (`max_borrow_days`, ค่าปรับ) |
| `equipment` (ครุภัณฑ์) | ต้องยืม-คืน มีทะเบียนรายชิ้น | มี (`asset_tag` เช่น `UBU-EQ-001-01`) | มี (`max_borrow_days`, ค่าปรับ) |

**หมายเหตุทั่วไป (Cross-cutting concern):** ทุก use case ในเอกสารนี้ (ยกเว้น UC-16 การเข้าสู่ระบบเอง) มีเงื่อนไขก่อนเริ่มทำงานร่วมกันคือ **ผู้ใช้ต้องเข้าสู่ระบบด้วยบริการ UBU Single Sign-On (@ubu.ac.th) และผ่านการตรวจสอบสิทธิ์และบทบาทเรียบร้อยแล้ว (`login_required` + ตรวจสอบ role/permission)** จึงไม่ระบุซ้ำในทุกแถว "เกี่ยวข้องกับ Service/Endpoint อื่น" ของแต่ละ use case ด้านล่าง

**หมายเหตุทั่วไป (การแจ้งเตือน):** เหตุการณ์ต่อไปนี้ ระบบจะแจ้งเตือนนักศึกษาโดยอัตโนมัติเสมอทั้ง 2 ช่องทาง คือ (1) การแจ้งเตือนในหน้าเว็บ (in-app) และ (2) อีเมล — ผลการอนุมัติ/ปฏิเสธคำขอยืม (UC-18), ถึงคิวที่จองไว้ (UC-11), ใกล้ครบกำหนดคืน/เกินกำหนดคืน (ต่อเนื่องจนกว่าจะแจ้งคืนสำเร็จที่ UC-09), ผลการพิจารณาคำเสนอแนะสิ่งของ (UC-29), และผลการตรวจรับเรื่องแจ้งซ่อม (UC-39) — เป็นพฤติกรรมอัตโนมัติของระบบที่ผูกกับ use case ของ actor แต่ละอันตามที่ระบุ ไม่แยกเป็น use case ใหม่ เพราะไม่มี actor ที่ริเริ่มการแจ้งเตือนเองโดยตรง จึงระบุไว้ที่นี่ครั้งเดียวแทนการเขียนซ้ำในทุก use case ที่เกี่ยวข้อง

> **ไม่มีอีกต่อไป (ตัดออกตาม mockup ปัจจุบัน):** สถานะ "อนุมัติแล้ว/รอรับของ" และกติกา auto-expire ถ้าไม่มารับของภายใน 2 วัน — เพราะ flow ปัจจุบันเป็น **On-the-Spot Counter Inspection**: นักศึกษาหยิบของมาวางหน้าเคาน์เตอร์ก่อนแล้วค่อยกดยืนยันคำขอ (`PENDING`) เจ้าหน้าที่ตรวจของจริงแล้วปล่อยทันทีในคลิกเดียว (`BORROWING`/`ISSUED`) ไม่มีช่วงเวลารอระหว่างอนุมัติกับรับของอีกต่อไป (ดู UC-06, UC-18 ที่แก้ไขใหม่)

## M1 · account (บัญชีและการเข้าสู่ระบบ)

> **แก้ไขรอบนี้:** ตัดทุกการอ้างอิง "Whitelist" ออก — รายชื่อบัญชีที่แอดมินเห็น (UC-33) มาจากบันทึกการเข้าสู่ระบบจริงผ่าน UBU SSO เท่านั้น (ไม่มีการอัปโหลด/ตั้งรายชื่อล่วงหน้าอีกต่อไป) ยกเว้น Role Override ที่แอดมินตั้งล่วงหน้าให้อีเมลที่ยังไม่เคย login ได้เป็นกรณีพิเศษ (ดู UC-34)

### E1 · การเข้าสู่ระบบ (ใช้ร่วมกันทุกบทบาท)

#### UC-16 · เข้าสู่ระบบด้วย UBU Single Sign-On

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-17 |
| **Actor หลัก** | นักศึกษา (Student), เจ้าหน้าที่ (Staff), ผู้ดูแลระบบ (Admin) |
| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | ผู้ใช้ทุกบทบาทต้องการเข้าสู่ระบบด้วยบัญชี UBU Single Sign-On (@ubu.ac.th) เพื่อเข้าใช้งานฟังก์ชันตามสิทธิ์ของตน โดยระบบจะยืนยันตัวตนและกำหนดบทบาทเริ่มต้น (Student/Staff) ตามข้อมูล SSO ของมหาวิทยาลัยโดยอัตโนมัติ เว้นแต่มีการกำหนดบทบาทเฉพาะบุคคล (Role Override) ไว้ล่วงหน้าโดยแอดมิน |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | ผู้ใช้มีบัญชี UBU Single Sign-On (@ubu.ac.th) ที่ถูกต้อง |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. ผู้ใช้กดเข้าสู่ระบบด้วย UBU Single Sign-On<br>2. ระบบพาไปยืนยันตัวตนกับบริการ UBU SSO (@ubu.ac.th)<br>3. ระบบได้รับข้อมูลการยืนยันตัวตนพร้อมสิทธิ์และประเภทบุคลากร และกำหนดบทบาทเริ่มต้น (Student/Staff) ตามข้อมูล SSO โดยอัตโนมัติ<br>4. ระบบบันทึก/อัปเดตบัญชีผู้ใช้ในระบบจากข้อมูล SSO ครั้งแรกที่ล็อกอิน (ไม่มีการตรวจสอบกับรายชื่อที่อัปโหลดล่วงหน้าใดๆ)<br>5. ระบบตรวจสอบว่าบัญชีนี้มีการกำหนดบทบาทเฉพาะบุคคล (Role Override, UC-34) ไว้หรือไม่ — ถ้ามี ใช้บทบาทที่ถูกกำหนดแทนบทบาทเริ่มต้นจาก SSO<br>6. ระบบสร้างเซสชันผู้ใช้ตามบทบาทที่ได้ และพาเข้าสู่หน้าหลักของบทบาทนั้น |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากการยืนยันตัวตนกับ UBU SSO ไม่สำเร็จ ระบบแสดงข้อความแจ้งเตือนข้อผิดพลาด<br>หากบัญชีถูกระงับสิทธิ์ (Block) โดยแอดมิน ระบบปฏิเสธการเข้าสู่ระบบ |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | ผู้ใช้มีเซสชันที่ยืนยันตัวตนแล้ว และเข้าใช้งานฟังก์ชันตามบทบาทที่แท้จริงของตนได้ (บทบาทจาก SSO หรือบทบาทที่ถูกกำหนดเฉพาะบุคคล) |
| **ความสัมพันธ์กับ Use Case อื่น** | เป็นเงื่อนไขก่อนเริ่มงาน (pre-condition) ร่วมของทุก use case อื่นในเอกสารนี้ |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **ลำดับความสำคัญของบทบาท:** Role Override (UC-34) มีผลเหนือกว่าบทบาทเริ่มต้นจาก UBU SSO เสมอ — การตรวจสอบต้องทำตามลำดับ SSO ก่อน แล้วจึงเช็ค Override ทับ ไม่ใช่ตรวจพร้อมกัน · **ไม่มีระบบ whitelist:** ไม่มีการอัปโหลด/ตั้งรายชื่อผู้มีสิทธิ์ล่วงหน้า บัญชีถูกสร้างขึ้นในระบบจากการ login ผ่าน SSO ครั้งแรกโดยอัตโนมัติเสมอ |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `account:login` → `LoginView` (บริการภายนอกจริง: UBU Single Sign-On) |

### E2 · ข้อมูลส่วนตัว (Student)

#### UC-14 · จัดการข้อมูลส่วนตัว

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-14, FR-15 |
| **Actor หลัก** | นักศึกษา (Student) |
| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | นักศึกษาต้องการดูและแก้ไขข้อมูลส่วนตัวของตนเอง เช่น เบอร์โทรศัพท์ เพื่อให้ข้อมูลติดต่อเป็นปัจจุบันและครบถ้วนสำหรับการยืมสิ่งของ พร้อมทั้งดูวันที่เข้าสู่ระบบครั้งแรก (First Login) และวันเวลาเข้าสู่ระบบครั้งล่าสุด (Last Login) ของตนเอง |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | นักศึกษาเข้าสู่ระบบแล้ว |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. นักศึกษาเปิดหน้าโปรไฟล์<br>2. ระบบแสดงข้อมูลส่วนตัว พร้อมวันที่เข้าสู่ระบบครั้งแรกและวันเวลาเข้าสู่ระบบครั้งล่าสุด (อ่านค่าจาก session/log ที่บันทึกไว้ตอน UC-16)<br>3. นักศึกษาแก้ไขข้อมูลติดต่อ เช่น เบอร์โทรศัพท์<br>4. ระบบบันทึกข้อมูลที่แก้ไข |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากข้อมูลติดต่อยังไม่ครบและนักศึกษาพยายามส่งคำขอยืม (UC-06) ระบบจะบังคับพากลับมาที่หน้านี้ก่อน (ตาม FR-15) |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | ข้อมูลส่วนตัวของนักศึกษาถูกอัปเดต และครบถ้วนพอสำหรับใช้ยืมสิ่งของ |
| **ความสัมพันธ์กับ Use Case อื่น** | เป็นเงื่อนไขก่อนเริ่มงาน (pre-condition) ของ UC-06 |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | - |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `account:profile_detail`, `account:profile_update` → `ProfileDetailView`, `ProfileUpdateView` (อ่านค่า `date_joined`/`last_login` ที่บันทึกไว้ตอนเข้าสู่ระบบใน UC-16) |

## M2 · catalog (ค้นหาและแสดงสิ่งของ)

### E1 · ค้นหาและแสดงสิ่งของ (Student)

| หัวข้อ | รายละเอียด |

| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | นักศึกษาต้องการดูรายการวัสดุสิ้นเปลือง วัสดุคงทน และครุภัณฑ์ทั้งหมดในคลัง (3 ประเภท) เพื่อสำรวจว่ามีสิ่งของอะไรให้ยืม/เบิกบ้างก่อนตัดสินใจ |

| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากคลังยังไม่มีสิ่งของ ระบบแสดงข้อความ "ยังไม่มีรายการสิ่งของ" |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | นักศึกษาเห็นภาพรวมของสิ่งของทั้งหมดในคลัง แยกตามประเภทและรายชิ้น (กรณีครุภัณฑ์) |
| **ความสัมพันธ์กับ Use Case อื่น** | ฐาน (base) ของ UC-02 (`<<extend>>`) และ UC-03 (`<<extend>>`) |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **การแสดงผลตามประเภท:** ครุภัณฑ์แสดงแยกรายชิ้นตาม Asset Tag เสมอ (ไม่รวมกลุ่ม) ส่วนวัสดุและวัสดุคงทนรวมกลุ่มแสดงเป็น SKU เดียวพร้อมจำนวนคงเหลือรวม |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `catalog:item_list` → `ItemListView` |

| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากไม่ได้แนบรูปภาพสภาพ ณ วันคืน ระบบแจ้งเตือนให้ถ่ายรูป/แนบรูปหลักฐานก่อนกดยืนยัน<br>นักศึกษายกเลิกการแจ้งคืนได้หากยังไม่สะดวกนำของมาจริง (กลับไปสถานะ "กำลังยืม" ตามเดิม) |

| **คำอธิบายโดยย่อ** | นักศึกษาต้องการจัดการคิวของตนเองแบบครบวงจร โดยจองคิวได้ 2 ระดับ: (ก) ระดับสิ่งของรวม (item-level) เมื่อวัสดุ/วัสดุคงทนเบิก/ยืมหมด และ (ข) ระดับรหัสครุภัณฑ์เฉพาะชิ้น (unit-level) เมื่อชิ้นนั้นถูกยืมอยู่แม้ item โดยรวมจะยังมีชิ้นอื่นว่างอยู่ก็ตาม |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | **กรณี item-level (วัสดุ/วัสดุคงทน):** สิ่งของนั้นมีจำนวนคงเหลือรวมเป็น 0 · **กรณี unit-level (ครุภัณฑ์):** รหัส Asset Tag ชิ้นที่เลือกมีสถานะ "ถูกยืมอยู่" (`BORROWED`) — ไม่เกี่ยวกับว่าชิ้นอื่นของ item เดียวกันยังว่างอยู่หรือไม่ |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. นักศึกษากดจองคิวจากหน้ารายการ/รายละเอียดสิ่งของ — เลือกจองคิว item รวม (วัสดุ/วัสดุคงทนหมดสต็อก) หรือจองคิวเฉพาะรหัส Asset Tag (ครุภัณฑ์ชิ้นที่ถูกยืมอยู่)<br>2. ระบบเพิ่มนักศึกษาเข้าคิวและแจ้งลำดับที่<br>3. นักศึกษาเปิดหน้ารายการคิวที่จองอยู่เพื่อติดตามลำดับ<br>4. นักศึกษากดออกจากคิวเมื่อไม่ต้องการยืมแล้ว |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากสิ่งของ/ชิ้นนั้นมีจำนวนคงเหลือ/ว่างอยู่แล้วในขณะนั้น ระบบไม่อนุญาตให้จองคิวและแนะนำให้ยืมได้ทันที<br>หากนักศึกษาอยู่ในคิวเดียวกันอยู่แล้ว ระบบแจ้งเตือน "คุณอยู่ในคิวแล้ว" ไม่ให้จองซ้ำ |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | คิวของนักศึกษาถูกสร้าง/ยกเลิกตามที่ดำเนินการ; เมื่อสิ่งของ/ชิ้นนั้นว่างและถึงคิวของนักศึกษาคนนั้น ระบบแจ้งเตือนผ่านหน้าเว็บและอีเมลทันที |
| **ความสัมพันธ์กับ Use Case อื่น** | `<<extend>>` จาก UC-05 (จองคิวแทนเมื่อถูกตัดหน้าในตะกร้า) และ UC-03 (จองคิวจากหน้ารายละเอียด) |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **แยกระดับคิวให้ชัด:** คิวระดับ item (ไม่มี `asset_tag`) ใช้กับวัสดุ/วัสดุคงทน ส่วนคิวระดับ unit (มี `asset_tag`) ใช้กับครุภัณฑ์เท่านั้น สองระดับนี้เป็นคนละคิวกัน แม้จะเป็น item เดียวกัน · **หมายเหตุตรวจสอบ:** ปัจจุบันข้อมูลคิวจริงยังไม่มีกติกาหมดเวลาอัตโนมัติหลังแจ้งเตือนถึงคิว (ไม่มีฟิลด์ `notified_at`/`expired_at` ใน mockup แม้ ERD เดิมจะออกแบบไว้) — จุดนี้ต้องยืนยันกับเจ้าของเอกสารว่าจะคงกติกาหมดเวลาไว้ตาม ERD หรือตัดออกให้ตรงกับ mockup (ดูหมายเหตุท้ายเอกสาร) |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `borrow:queue_join`, `borrow:queue_list`, `borrow:queue_leave` → `QueueJoinView`, `QueueListView`, `QueueLeaveView` |

## M5 · evaluation (การประเมินความพึงพอใจและรีวิว)

> **แก้ไขรอบนี้:** UC-15 เดิมไม่มี flow เขียนรีวิวผูก Asset Tag (conflict ที่ค้างมาจากรอบตรวจก่อนหน้า) — mockup ปัจจุบัน **มีการเขียนรีวิวจริงแล้ว** ที่หน้าประเมิน จึงรวมเข้าเป็น flow เดียวกับ UC-15 (ประเมินทีละชิ้นอิสระ + เขียนรีวิวอัตโนมัติเมื่อชิ้นนั้นเป็นครุภัณฑ์)

### E1 · การประเมินของนักศึกษา

#### UC-15 · ประเมินความพึงพอใจรายชิ้นและเขียนรีวิว

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-16 |
| **Actor หลัก** | นักศึกษา (Student) |
| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | นักศึกษาต้องการประเมินความพึงพอใจและสภาพการใช้งานของสิ่งของที่คืนแล้ว **แยกเป็นรายชิ้นอย่างอิสระ** (ไม่ถูกบังคับให้ประเมินพร้อมกันทุกชิ้นในคำขอเดียวกัน) โดยสำหรับครุภัณฑ์ คะแนนดาวและข้อความรีวิวจะถูกบันทึกผูกเข้ากับรหัส Asset Tag ของชิ้นนั้นโดยอัตโนมัติ เพื่อให้ผู้ยืมคนถัดไปใช้ประกอบการตัดสินใจ (ดู UC-38) |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | นักศึกษาเข้าสู่ระบบแล้ว และมีสิ่งของที่คืนสำเร็จแล้วอย่างน้อย 1 ชิ้นที่ยังไม่เคยประเมิน |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. นักศึกษาเปิดหน้าประเมิน (จากเมนู หรือกดปุ่ม `⭐ ประเมินชิ้นนี้` จากหน้ารายการคำขอ/ประวัติ UC-10/UC-12)<br>2. ระบบแสดงแถบการ์ดรายชิ้นของสิ่งของที่คืนแล้วทั้งหมด พร้อมสถานะ: `✓ ประเมินแล้ว (คะแนน)` / `⭐ รอประเมิน` / `✍️ กำลังประเมิน`<br>3. นักศึกษาเลือกชิ้นที่ต้องการประเมิน ให้คะแนนดาว 1-5 ดาว ติ๊กสภาพความพร้อมใช้งาน และเขียนข้อความรีวิว<br>4. กดยืนยันการส่งแบบประเมินของชิ้นนั้น<br>5. ระบบบันทึกผลการประเมินลง `eval_responses` ผูกกับคำขอและชิ้นนั้น (`orig_item_idx`/`asset_tag`)<br>6. **หากชิ้นนั้นเป็นครุภัณฑ์ (มีรหัส Asset Tag)** ระบบบันทึกคะแนนดาวและข้อความรีวิวเพิ่มเข้าไปในประวัติรีวิวของรหัส Asset Tag นั้นโดยอัตโนมัติ (ผูกกับชิ้นนั้นเท่านั้น ไม่ใช่ผูกรวมทั้งหมวด) และคำนวณคะแนนดาวเฉลี่ยของชิ้นนั้นใหม่<br>7. ระบบเลื่อนไปยังชิ้นถัดไปที่ยังไม่ได้ประเมินโดยอัตโนมัติ (ถ้ามี) |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากชิ้นนั้นถูกประเมินไปแล้ว ระบบแสดงผลการประเมินเดิมแทนฟอร์มกรอกใหม่ (ไม่ให้ประเมินซ้ำ) |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | ผลการประเมินของชิ้นนั้นถูกบันทึก และหากเป็นครุภัณฑ์ รีวิว/คะแนนดาวของรหัส Asset Tag ชิ้นนั้นถูกอัปเดตให้ผู้ยืมคนถัดไปเห็นทันที (UC-38) |
| **ความสัมพันธ์กับ Use Case อื่น** | ต่อเนื่องจาก UC-09/UC-19 (คืนสำเร็จ); เขียนข้อมูลที่ UC-38 นำไปแสดง |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **ประเมินได้ 1 ครั้งต่อชิ้น** ไม่ใช่ 1 ครั้งต่อแบบฟอร์มทั้งชุดเหมือนเดิม — นักศึกษาประเมินแต่ละชิ้นในคำขอเดียวกันแยกอิสระได้ **ผูกรีวิวกับ Asset Tag รายชิ้น:** เฉพาะชิ้นที่เป็นครุภัณฑ์เท่านั้นที่มีการเขียนรีวิวเก็บสะสมต่อรหัสชิ้น วัสดุ/วัสดุคงทนบันทึกผลประเมินไว้ที่ `eval_responses` อย่างเดียวไม่ผูกกับ asset tag ใด |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `evaluation:submit` → `EvaluationSubmitView` (เขียนทั้ง `eval_responses` และ `units.reviews` เมื่อเป็นครุภัณฑ์) |

### E2 · การจัดการคำขอยืม-คืน

#### UC-18 · ตรวจของและปล่อยของหน้าเคาน์เตอร์ (On-the-Spot Counter Inspection)

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-19, FR-08 (ยุบรวม — ดู UC-08) |

| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | เจ้าหน้าที่ต้องการตรวจนับสิ่งของจริงที่นักศึกษานำมาวางหน้าเคาน์เตอร์เทียบกับคำขอในระบบ แล้วปล่อยของและปฏิเสธเป็นรายชิ้นได้ในขั้นตอนเดียว โดยไม่มีขั้นตอนอนุมัติแล้วรอรับของแยกต่างหากอีกต่อไป |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | มีคำขอยืมสถานะ "รอเจ้าหน้าที่ตรวจของ" (`PENDING`) ในระบบ (ที่ส่งจาก UC-06) |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. เจ้าหน้าที่เปิดหน้ารายการคำขอที่รอตรวจของ<br>2. ตรวจนับของจริงบนโต๊ะเทียบกับรายการในคำขอ โดยติ๊ก checkbox รายชิ้น (ค่าเริ่มต้นติ๊กถูกทุกชิ้น) — ชิ้นที่ของขาด/นักศึกษาเปลี่ยนใจไม่รับ ให้ติ๊กออก<br>3. กดดูรูปถ่ายสภาพสิ่งของที่นักศึกษาแนบมาได้ (ถ้ามี, `initial_photo`)<br>4. หากเป็นคำขอยืมพิเศษ (`is_special`) เจ้าหน้าที่ตรวจสอบเหตุผลและปรับวันที่อนุญาตคืนได้ก่อนอนุมัติ<br>5. กด `✓ ตรวจของครบแล้ว — ปล่อยของ` เพื่อยืนยัน หรือกด `✕ ปฏิเสธคำขอ` พร้อมระบุเหตุผล<br>6. เมื่อปล่อยของ ระบบตัดสต็อกคลัง (`qty_available`) เฉพาะชิ้นที่ติ๊กว่านำไปจริง เปลี่ยนสถานะรหัสครุภัณฑ์ที่ปล่อยเป็น `BORROWED` และบันทึกเวลาอนุมัติกับเวลารับของเป็นเวลาเดียวกัน |

| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | หากคำขอมีครุภัณฑ์หรือวัสดุคงทนแม้แต่ชิ้นเดียว → คำขอเปลี่ยนเป็น "กำลังยืม" (`BORROWING`) ทันทีพร้อมกำหนดวันคืน; หากมีเฉพาะวัสดุสิ้นเปลืองล้วน → คำขอเปลี่ยนเป็น "เบิกสำเร็จ" (`ISSUED`) ทันที; หรือคำขอเปลี่ยนเป็น "ปฏิเสธแล้ว" (`REJECTED`) พร้อมเหตุผล — ทุกกรณีส่งแจ้งเตือนให้นักศึกษา |
| **ความสัมพันธ์กับ Use Case อื่น** | ต่อยอดจาก UC-06 (นักศึกษาส่งคำขอ); ยุบรวม UC-08 (ยืนยันรับสิ่งของ) เข้ามาในขั้นตอนที่ 6 |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **ตัดจ่ายอัตโนมัติตามรหัสที่เลือก:** เจ้าหน้าที่ไม่ต้องกดเลือก Dropdown สลับรหัสชิ้น ระบบตัดจ่ายตามรหัส Asset Tag ที่นักศึกษาเลือกไว้ตอนลงตะกร้า/ส่งคำขอ · **ไม่มีสถานะ "อนุมัติแล้ว/รอรับของ" อีกต่อไป** และไม่มี auto-expire 2 วัน เพราะอนุมัติกับรับของเกิดขึ้นพร้อมกันเสมอ |

| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. เจ้าหน้าที่เปิดหน้ารับคืนพัสดุ — กรองแท็บได้: ทั้งหมด / รอตรวจรับคืน / เกินกำหนด / คืนบางส่วน<br>2. ชิ้นที่นักศึกษาแจ้งคืนมาแล้วถูกติ๊กนำร่องให้อัตโนมัติ (Smart Pre-check) เจ้าหน้าที่ตรวจของจริงบนโต๊ะเทียบกับที่ติ๊กไว้ (ใช้ปุ่ม `✓ เลือกทั้งหมด` ได้)<br>3. ต่อแต่ละชิ้นที่ตรวจ เลือกผลตรวจสภาพจริง: **ปกติ** (คืนสต็อกเข้าคลัง, ครุภัณฑ์กลับเป็น `AVAILABLE`) / **ชำรุด** (ครุภัณฑ์เปลี่ยนเป็น `DAMAGED` ไม่คืนสต็อก และสร้างรายการแจ้งซ่อมอัตโนมัติ — เชื่อม UC-36) / **สูญหาย** (ครุภัณฑ์เปลี่ยนเป็น `LOST`, ตัดสต็อกรวมถาวร `qty_total -= 1`, ระบบตั้งยอดชดใช้เริ่มต้นจากราคาจัดซื้อเดิม ปรับแก้ได้ พร้อมปุ่มบันทึกรับชำระเงิน)<br>4. ระบบคำนวณค่าปรับเกินกำหนดอัตโนมัติจากจำนวนวันที่เกิน `due_date` (ดู UC-37) เจ้าหน้าที่กด `✏️ แก้ไขยอดเงิน` เพื่อปรับยอด (`custom_fine`) และกดสลับสถานะ `fine_paid` เมื่อนักศึกษาชำระแล้วได้<br>5. กดยืนยันรับคืน |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | **คืนครบทุกชิ้นที่ต้องคืน** → คำขอเปลี่ยนเป็น "คืนสำเร็จ" (`RETURNED`) สมบูรณ์<br>**คืนบางชิ้น** (ของขาด/ยังใช้ต่อ) → รับคืนเฉพาะชิ้นที่นำมา ชิ้นที่ขาดคงสถานะ "กำลังยืม" (`BORROWING`) ต่อไป และบันทึกข้อความสรุป เช่น "คืนแล้ว 1 ชิ้น (ยังค้างส่งอีก 1 ชิ้น)" (`return_summary`) |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | คำขอเปลี่ยนสถานะตามผลตรวจ (คืนสำเร็จ/คืนบางส่วน) พัสดุที่สภาพปกติถูกคืนเข้าคลังพร้อมให้ยืมต่อ ครุภัณฑ์ชำรุดเข้าสู่ระบบแจ้งซ่อม (UC-36) ครุภัณฑ์สูญหายถูกตัดออกจากคลังถาวรพร้อมบันทึกยอดชดใช้ และบันทึกค่าปรับ/สถานะการชำระเงินเรียบร้อย |
| **ความสัมพันธ์กับ Use Case อื่น** | รับช่วงต่อจาก UC-09 (นักศึกษาแจ้งคืน); ทำงานร่วมกับ UC-37 (จัดการค่าปรับ); ส่งต่อไปยัง UC-36 (ครุภัณฑ์เสียหาย) กรณีชำรุด |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **คืนสต็อกอัตโนมัติเฉพาะกรณีปกติ:** เพิ่มจำนวนพร้อมใช้งานกลับเข้าคลังเฉพาะชิ้นที่ตรวจสภาพปกติเท่านั้น · **ชำรุด→เปลี่ยนสถานะทันที ไม่ต้องรอ UC-24:** ครุภัณฑ์ที่ตรวจพบว่าเสียหายเปลี่ยนเป็น "ครุภัณฑ์เสียหาย" อัตโนมัติทันทีที่ตรวจรับคืน · **สูญหาย→ตัดสต็อกถาวร:** ต่างจากชำรุดตรงที่ตัด `qty_total` ถาวรทันที ไม่ใช่แค่เปลี่ยนสถานะรอซ่อม |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `staff:return_list`, `staff:return_confirm`, `staff:edit_fine` → `ReturnConfirmView` |

#### UC-37 · กำหนดอัตราค่าปรับและจัดการการชำระค่าปรับเกินกำหนด

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-26, FR-37 |
| **Actor หลัก** | เจ้าหน้าที่ (Staff), ผู้ดูแลระบบ (Admin) |

| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. เจ้าหน้าที่เปิดหน้าตั้งค่าคลัง แท็บ "อัตราค่าปรับ" หรือ หน้ารายการรับคืนครุภัณฑ์<br>2. ตั้งค่าอัตราค่าปรับกลางต่อวัน (ค่าเริ่มต้น 10 บาท/วัน) แล้วระบบบันทึกค่าไว้<br>3. เมื่อมีรายการยืมเกินกำหนด ระบบคำนวณยอดค่าปรับ = `จำนวนวันเกินกำหนด × อัตราค่าปรับต่อวัน`<br>4. ในหน้ารับคืน (UC-19) เจ้าหน้าที่สามารถกดปุ่ม `✏️ แก้ไขยอดเงิน` กรอกยอดเงินค่าปรับใหม่ (`custom_fine`) เพื่อปรับลดหรือยกเว้นค่าปรับเป็น 0 บาทได้<br>5. เมื่อนักศึกษานำเงินมาชำระแล้ว เจ้าหน้าที่กดปุ่มสลับสถานะชำระค่าปรับเป็น "ชำระแล้ว (`fine_paid = true`)" |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากเจ้าหน้าที่ไม่ได้ระบุ `custom_fine` ระบบจะใช้ยอดคำนวณอัตโนมัติตามอัตราค่าปรับต่อวัน<br>หากนักศึกษายังไม่ชำระค่าปรับ สถานะจะแสดงเป็น "ค้างชำระ" และแสดงเตือนในหน้าประวัติยืมของนักศึกษา |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | อัตราค่าปรับถูกอัปเดต ยอดค่าปรับรายคำขอถูกบันทึก และสถานะการชำระเงินถูกบันทึกในระบบ |
| **ความสัมพันธ์กับ Use Case อื่น** | ทำงานร่วมกับ UC-19 (ตรวจรับคืน) และ UC-26 (จัดการตั้งค่าคลัง) |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **สิทธิ์ปรับลดค่าปรับ:** เจ้าหน้าที่และแอดมินมีสิทธิ์กดแก้ไขยอดค่าปรับ (`custom_fine`) หรือยกเว้นค่าปรับ (ตั้งเป็น 0) ได้ตามดุลยพินิจ · **ค่าเริ่มต้นที่ถูกต้องคือ 10 บาท/วัน** (ยึดตามค่าจริงใน `shared.js` ไม่ใช่ 20 บาทตามที่เอกสารบันทึกการเปลี่ยนแปลงบางฉบับเขียนคลาดเคลื่อนไว้) |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `staff:fine_setting`, `staff:update_custom_fine`, `staff:toggle_fine_paid` → `FineSettingView`, `FineManagementView` |

| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | เจ้าหน้าที่เห็นรายการซ่อมทั้งหมดที่ต้องติดตามทั้ง 2 ที่มา และปรับสถานะต่อได้ |
| **ความสัมพันธ์กับ Use Case อื่น** | รับรายการเข้ามาโดยอัตโนมัติจาก UC-19 (แท็บ 1) และจาก UC-39 (แท็บ 2) — คนละรอบเวลา (asynchronous) จึงไม่ใช่ `<<include>>`/`<<extend>>` เชิง UML แม้เป็น actor เดียวกัน (Staff) ก็ตาม; เชื่อมต่อไปยัง UC-24 กรณีต้องเปลี่ยนสถานะครุภัณฑ์เพิ่มเติม (เช่น ปลดระวาง) |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | เมื่อเจ้าหน้าที่ตรวจรับคืนครุภัณฑ์ (UC-19) แล้วพบว่าเสียหาย ระบบต้องเปลี่ยนสถานะรหัสครุภัณฑ์ชิ้นนั้นจาก "พร้อมให้ยืม" เป็น "ครุภัณฑ์เสียหาย" โดยอัตโนมัติทันที ไม่ต้องรอเจ้าหน้าที่ไปตั้งค่าเองที่ UC-24 · รายการแจ้งซ่อมจาก UC-39 ไม่ผูกกับประวัติการยืมใดๆ (นักศึกษาแจ้งได้แม้ไม่เคยยืมของชิ้นนั้น) |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `staff:damaged_equipment_list`, `staff:damaged_equipment_update_status`, `staff:damage_report_review` → `DamagedEquipmentListView` |
