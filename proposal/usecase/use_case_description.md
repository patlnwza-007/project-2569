# YuemDee · ระบบยืม-คืนพัสดุออนไลน์ มหาวิทยาลัยอุบลราชธานี — Use Case Description

> อ้างอิงจาก `yuemdee_functional_requirements.md` (v1.3) — 1 use case ในเอกสารนี้ต้องตรงกับ 1 use case ใน `usecase.puml` (UC-01 ถึง UC-36)
> ผู้ใช้งาน 3 บทบาท: 🎓 นักศึกษา (Student), 👷 เจ้าหน้าที่ (Staff), 👑 ผู้ดูแลระบบ (Admin)
> จัดกลุ่มเป็น 10 Module (M1–M10) ตาม Django app หลังยุบรวม (ดูตารางสรุปท้ายเอกสาร) แต่ละ module แบ่งเป็น Epic (E1, E2...) ภายใน

**หมายเหตุทั่วไป (Cross-cutting concern):** ทุก use case ในเอกสารนี้ (ยกเว้น UC-16 การเข้าสู่ระบบเอง) มีเงื่อนไขก่อนเริ่มทำงานร่วมกันคือ **ผู้ใช้ต้องเข้าสู่ระบบด้วยบริการ UBU Single Sign-On (@ubu.ac.th) และผ่านการตรวจสอบสิทธิ์และบทบาทเรียบร้อยแล้ว (`login_required` + ตรวจสอบ role/permission)** จึงไม่ระบุซ้ำในทุกแถว "เกี่ยวข้องกับ Service/Endpoint อื่น" ของแต่ละ use case ด้านล่าง

**หมายเหตุทั่วไป (การแจ้งเตือน):** เหตุการณ์ต่อไปนี้ ระบบจะแจ้งเตือนนักศึกษาโดยอัตโนมัติเสมอทั้ง 2 ช่องทาง คือ (1) การแจ้งเตือนในหน้าเว็บ (in-app) และ (2) อีเมล — ผลการอนุมัติ/ปฏิเสธคำขอยืม (UC-18), ถึงคิวที่จองไว้ (UC-11), ใกล้ครบกำหนดคืน/เกินกำหนดคืนของครุภัณฑ์ (ต่อเนื่องจาก UC-08 จนกว่าจะแจ้งคืนสำเร็จที่ UC-09), คำขอถูกยกเลิกอัตโนมัติเพราะไม่มารับของภายใน 2 วัน (UC-18), และผลการพิจารณาคำเสนอแนะสิ่งของ (UC-29) — เป็นพฤติกรรมอัตโนมัติของระบบที่ผูกกับ use case ของ actor แต่ละอันตามที่ระบุ ไม่แยกเป็น use case ใหม่ เพราะไม่มี actor ที่ริเริ่มการแจ้งเตือนเองโดยตรง จึงระบุไว้ที่นี่ครั้งเดียวแทนการเขียนซ้ำในทุก use case ที่เกี่ยวข้อง

## M1 · account (บัญชีและการเข้าสู่ระบบ)

### E1 · การเข้าสู่ระบบ (ใช้ร่วมกันทุกบทบาท)

#### UC-16 · เข้าสู่ระบบด้วย UBU Single Sign-On

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-17 |
| **Actor หลัก** | นักศึกษา (Student), เจ้าหน้าที่ (Staff), ผู้ดูแลระบบ (Admin) |
| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | ผู้ใช้ทุกบทบาทต้องการเข้าสู่ระบบด้วยบัญชี UBU Single Sign-On (@ubu.ac.th) เพื่อเข้าใช้งานฟังก์ชันตามสิทธิ์ของตน โดยระบบจะยืนยันตัวตนและกำหนดบทบาทเริ่มต้น (Student/Staff) ตามข้อมูล SSO ของมหาวิทยาลัยโดยอัตโนมัติ เว้นแต่มีการกำหนดบทบาทเฉพาะบุคคล (Role Override) ไว้ล่วงหน้าโดยแอดมิน |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | ผู้ใช้มีบัญชี UBU Single Sign-On (@ubu.ac.th) ที่ถูกต้อง |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. ผู้ใช้กดเข้าสู่ระบบด้วย UBU Single Sign-On<br>2. ระบบพาไปยืนยันตัวตนกับบริการ UBU SSO (@ubu.ac.th)<br>3. ระบบได้รับข้อมูลการยืนยันตัวตนพร้อมสิทธิ์และประเภทบุคลากร และกำหนดบทบาทเริ่มต้น (Student/Staff) ตามข้อมูล SSO โดยอัตโนมัติ<br>4. ระบบตรวจสอบว่าบัญชีนี้มีการกำหนดบทบาทเฉพาะบุคคล (Role Override, UC-34) ไว้หรือไม่ — ถ้ามี ใช้บทบาทที่ถูกกำหนดแทนบทบาทเริ่มต้นจาก SSO<br>5. ระบบสร้างเซสชันผู้ใช้ตามบทบาทที่ได้ และพาเข้าสู่หน้าหลักของบทบาทนั้น |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากการยืนยันตัวตนกับ UBU SSO ไม่สำเร็จ ระบบแสดงข้อความแจ้งเตือนข้อผิดพลาด<br>หากบัญชีถูกระงับสิทธิ์ (Block) โดยแอดมิน ระบบปฏิเสธการเข้าสู่ระบบ |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | ผู้ใช้มีเซสชันที่ยืนยันตัวตนแล้ว และเข้าใช้งานฟังก์ชันตามบทบาทที่แท้จริงของตนได้ (บทบาทจาก SSO หรือบทบาทที่ถูกกำหนดเฉพาะบุคคล) |
| **ความสัมพันธ์กับ Use Case อื่น** | เป็นเงื่อนไขก่อนเริ่มงาน (pre-condition) ร่วมของทุก use case อื่นในเอกสารนี้ |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **ลำดับความสำคัญของบทบาท:** Role Override (UC-34) มีผลเหนือกว่าบทบาทเริ่มต้นจาก UBU SSO เสมอ — การตรวจสอบต้องทำตามลำดับ SSO ก่อน แล้วจึงเช็ค Override ทับ ไม่ใช่ตรวจพร้อมกัน |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `account:login` → `LoginView` (บริการภายนอกจริง: UBU Single Sign-On) |

### E2 · ข้อมูลส่วนตัว (Student)

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-14, FR-15 |
| **Actor หลัก** | นักศึกษา (Student) |
| **Actor รอง** | - |

| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | นักศึกษาเข้าสู่ระบบแล้ว |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. นักศึกษาเปิดหน้าโปรไฟล์<br>2. ระบบแสดงข้อมูลส่วนตัว พร้อมวันที่เข้าสู่ระบบครั้งแรกและวันเวลาเข้าสู่ระบบครั้งล่าสุด (อ่านค่าจาก session/log ที่บันทึกไว้ตอน UC-16)<br>3. นักศึกษาแก้ไขข้อมูลติดต่อ เช่น เบอร์โทรศัพท์<br>4. ระบบบันทึกข้อมูลที่แก้ไข |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | หากข้อมูลติดต่อยังไม่ครบและนักศึกษาพยายามส่งคำขอยืม (UC-06) ระบบจะบังคับพากลับมาที่หน้านี้ก่อน (ตาม FR-15) |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | ข้อมูลส่วนตัวของนักศึกษาถูกอัปเดต และครบถ้วนพอสำหรับใช้ยืมสิ่งของ |
| **ความสัมพันธ์กับ Use Case อื่น** | เป็นเงื่อนไขก่อนเริ่มงาน (pre-condition) ของ UC-06 |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | - |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `account:profile_detail`, `account:profile_update` → `ProfileDetailView`, `ProfileUpdateView` (อ่านค่า `date_joined`/`last_login` ที่บันทึกไว้ตอนเข้าสู่ระบบใน UC-16) |

| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | - |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `admin_panel:user_list`, `admin_panel:user_detail`, `admin_panel:user_delete`, `admin_panel:user_block`, `admin_panel:user_unblock` → `UserListView`, `UserDetailView`, `UserDeleteView`, `UserBlockView`, `UserUnblockView` |

### E2 · การกำหนดบทบาท (Role Override)

#### UC-34 · กำหนดบทบาทผู้ใช้เป็นรายบุคคล (Role Override)

| หัวข้อ | รายละเอียด |
|-------|-----------|
| **รหัสอ้างอิง** | FR-34 |
| **Actor หลัก** | ผู้ดูแลระบบ (Admin) |
| **Actor รอง** | - |
| **คำอธิบายโดยย่อ** | แอดมินต้องการกำหนด/เปลี่ยนบทบาทของผู้ใช้เป็นรายบุคคล เพื่อรองรับกรณีพิเศษที่บทบาทอัตโนมัติจาก UBU SSO ไม่ตรงกับบทบาทจริงที่ควรได้รับ เช่น นักศึกษาที่เป็นหัวหน้าห้องต้องได้รับสิทธิ์แบบเจ้าหน้าที่ (Staff) ทั้งที่มีบทบาทเริ่มต้นเป็นนักศึกษาจาก UBU SSO |
| **เงื่อนไขก่อนเริ่มทำงาน (Pre-condition)** | แอดมินเลือกผู้ใช้งานเป้าหมายจากรายชื่อแล้ว (UC-33) |
| **ลำดับเหตุการณ์หลัก (Basic Flow)** | 1. แอดมินเปิดหน้ารายรายละเอียดผู้ใช้งานที่เลือก<br>2. แอดมินเลือกบทบาทที่ต้องการกำหนด (เช่น เปลี่ยนจาก Student เป็น Staff) พร้อมระบุเหตุผล (ไม่บังคับ)<br>3. ระบบบันทึกบทบาทที่ถูกกำหนด (Role Override) ไว้กับบัญชีนั้น |
| **ลำดับเหตุการณ์ทางเลือก (Alternative/Exception Flow)** | แอดมินยกเลิกบทบาทที่เคยกำหนดไว้ได้ (กลับไปใช้บทบาทอัตโนมัติจาก UBU SSO ตามปกติ) |
| **เงื่อนไขหลังทำงานสำเร็จ (Post-condition)** | บัญชีผู้ใช้งานมีบทบาทตามที่กำหนดไว้ มีผลตั้งแต่การเข้าสู่ระบบครั้งถัดไป (UC-16) โดยมีผลเหนือกว่าบทบาทเริ่มต้นจาก UBU SSO เสมอ |
| **ความสัมพันธ์กับ Use Case อื่น** | `<<include>>` UC-33; เป็นเงื่อนไขก่อนเริ่มงาน (pre-condition) ที่มีผลต่อ UC-16 |
| **กฎทางธุรกิจที่เกี่ยวข้อง (Business Rules)** | **ผลเหนือกว่า UBU SSO เสมอ:** บทบาทที่กำหนดผ่าน Role Override มีผลเหนือกว่าบทบาทเริ่มต้นจาก UBU SSO ทุกกรณี ไม่ว่าจะยกเลิกและกำหนดใหม่กี่ครั้งก็ตาม จนกว่าแอดมินจะยกเลิก Override จึงกลับไปใช้บทบาทจาก UBU SSO ตามปกติ |
| **เกี่ยวข้องกับ Service/Endpoint อื่น** | `admin_panel:user_role_override` → `UserRoleOverrideView` |
